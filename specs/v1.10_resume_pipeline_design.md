# v1.10 静默续跑决策、投递与核验设计

> 状态：v1.10.0 收尾实现说明
> 日期：2026-08-07
> 核心目标：自动续跑必须静默、精确、幂等、可验证；不满足条件时延后，而不是抢焦点盲敲

## 1. 问题定义

旧实现把“检测到疑似中断”“脚本成功退出”“Agent 已收到提示词”混成一次布尔操作，也把进程实例近似当作逻辑会话。这会产生四类用户可感知问题：

1. 检测抖动时重复续跑；
2. 后台通道不可用时弹窗、抢焦点或把文本敲进当前工作窗口；
3. Windows cmd/conhost 中只提交 Enter，文本没有进入，API 却报告成功；
4. 同一逻辑会话跨进程重启后在历史页裂成多条重复记录。

v1.10 将其拆成：**身份 → 连续观测决策 → 能力许可 → 幂等 attempt → 不可逆投递 → 精确核验 → 最终记账**。

## 2. 安全能力模型

`resume_core.rs` 定义与平台无关的能力维度：

```text
DeliveryPolicy: BackgroundOnly | AllowForeground
TargetCertainty: Exact | Window | Unknown
Visibility: Background | StealsFocus
Verification: Transcript | Protocol | None
```

自动策略只有在以下条件全部满足时才允许：

```text
policy == BackgroundOnly
&& target == Exact
&& visibility == Background
&& verification != None
```

手动策略 `AllowForeground` 表示用户已明确授权这一次前台动作，但仍不允许 `Unknown` 目标。自动模式绝不隐式升级为手动模式。

没有安全通道时返回稳定结果：

```text
deferred/no-safe-transport
```

`Deferred` 不算成功、不算失败、不消耗续跑连击额度，也不应刷失败通知。

## 3. v1.10 通道矩阵

| 场景 | 自动 `BackgroundOnly` | 手动 `AllowForeground` | 核验 |
|---|---|---|---|
| tmux exact pane | 允许，`send-keys -t <pane>` | 允许 | 必须有 transcript |
| screen 当前 window | 延后：不是精确 pane | 可在显式盲跟随策略下使用 | 有 transcript 才可确认 |
| macOS iTerm2 exact TTY | 允许后台 `write text`，不 `activate`、不 `select` | 允许前台兼容路径 | 必须有 transcript |
| macOS Terminal.app / IDE 终端 | 延后 | 可前台定位后输入 | transcript 精确 prompt |
| Windows classic cmd/conhost | 延后：外部 console 无法按 PID 获得精确输入端点 | 用户点击后可前台定位并用 Unicode `SendInput` | transcript 精确 prompt |
| Windows Terminal / ConPTY / IDE 终端 | 延后：外部既有会话无精确后台端点 | 用户点击后可前台定位并用 Unicode `SendInput` | transcript 精确 prompt |
| Linux X11 / Wayland 普通终端 | 延后 | 可显式使用 xdotool/ydotool 路径 | transcript 精确 prompt |
| 无 transcript/协议确认 | 延后 | 可手动投递，但结果不得伪装成已验证 | `Unverifiable` |

这张表描述代码能力边界，不代表所有平台已经完成真机验收。

## 4. Windows 外部 console 的安全边界

旧路径通过剪贴板与 `Ctrl+V` 投递。cmd/conhost 没有消费组合键时，Codex CLI 把它解释为“粘贴图片”，产生：

```text
Failed to paste image: no image on clipboard
```

`AttachConsole` / `GetConsoleProcessList` 可以证明进程属于某个 console，`WriteConsoleInputW` 可以写入
该 console 的共享输入缓冲，但这些事实不能构成“只投递给目标 PID/CLI”的精确寻址。外部 Windows
console 不是 AgentPulse 拥有的 transport；同一 console 中的输入消费者、前台读取状态和宿主行为
不受 AgentPulse 控制。因此该路径不得进入自动 `BackgroundOnly` 能力集合。

v1.10 的约束是：

1. 外部 classic cmd/conhost、Windows Terminal/ConPTY 和 IDE terminal 的自动路径返回 `Deferred/no-safe-transport`；
2. 自动模式不激活窗口、不发送键盘事件，也不因 `auto_follow_latest` 降级为前台输入；
3. 只有用户明确点击手动续跑，才可进入 `AllowForeground`；
4. 手动路径在输入前重新核验进程代际与唯一窗口目标，无法唯一定位或目标已失效时拒绝；
5. 手动输入使用 Unicode `SendInput` 发送完整 prompt，文本完成后独立发送 Enter；
6. 不访问或覆盖剪贴板，不发送 `Ctrl+V` / `SendKeys`，不弹出可见 PowerShell 窗口；
7. transport 返回成功仍不等于 `Landed`，最终结果继续依赖 transcript 中的精确 prompt；
8. Unicode 完整性、独立 Enter、焦点边界与 Codex CLI 实际消费行为必须在 Windows 真机复测。

Owned ConPTY 或官方/server 协议只有在 AgentPulse 持有明确的会话输入端点时，才可能在后续版本成为
Windows 安全后台 transport；不能用外部 PID + 共享 console buffer 替代这个所有权边界。

## 5. 连续观测 reducer

一次扫描命中不直接授予投递许可。`reduce_decision` 是纯函数，状态为：

```text
Observing
  └─ confirmed evidence → Suspected { evidence_hash, observations }
Suspected
  ├─ same evidence reaches threshold → Eligible { decision_id, evidence_hash }
  ├─ evidence changes → new Suspected
  └─ healthy/suspicious → Observing
Eligible
  ├─ same evidence → keep same decision identity
  └─ changed/healthy → reset or start new evidence window
```

`idle_threshold` 表示连续观测次数，不再通过重复乘时间伪装稳定性。`evidence_hash` 只包含稳定结构证据，不包含每轮变化的“已空闲 N 秒”文案，避免永远无法达到 Eligible。

## 6. Attempt Ledger

SQLite 表 `resume_attempts` 保存不可逆动作的事务状态，核心字段包括：

```text
attempt_id, decision_id, session_generation, session_id,
evidence_hash, prompt_hash, state, failure_class, baseline_cursor,
created_at, delivery_started_at, transport_acked_at, verified_at, next_retry_at
```

幂等键：

```text
UNIQUE(session_generation, evidence_hash, prompt_hash)
```

`begin_attempt` 使用 SQLite `IMMEDIATE` 事务，竞争调用只能有一个得到 `Created`，其余得到 `Existing`。唯一键定义精确动作；此外任意 prompt 下的危险状态都会对整个 `session_generation` 建立防重放栅栏，提示词热更新不能绕过未决外部副作用。状态 API 区分：

```text
created → delivering → transport_acked → verified
    ├──────────────→ deferred | failed
    └──────────────→ unverifiable
```

其中：

- `delivery_started_at` 必须在调用不可回滚 transport 之前落库；
- transport ACK 不是 verified；
- deferred 表示当前没有安全能力，不是失败；只有设置了有效且已到期 `next_retry_at` 的 deferred 可重新 CAS 进入投递，其他 Existing 状态都不得重放；
- verified 只能由 transcript 或协议证据确认；
- v1.10 自动链已接入 begin、delivery_started、transport_acked、verified/deferred/unverifiable/failed 更新；只有通过单实例仲裁的主实例会在 setup 阶段把遗留 delivering/acked 原子收敛为 unverifiable，created 可恢复 claim，deferred 到期后可安全重试；任意 prompt 下的危险状态都会按整个 generation 阻断重放，最终 `delivery_started` claim 也在 SQLite 原子更新中按 generation 重新确认单赢家。transcript 补核验、typed backoff/quarantine 属于后续计划。

## 7. 不可逆投递与只读核验

协调器继续使用按 runtime generation 合并的队列、runtime-generation lease、全局 `delivery_lock` 和 lifecycle epoch：

1. 扫描只发现、取证并生成候选动作；
2. 同 session 多轮命中只保留最新快照；
3. worker 可绕过仍在核验的忙 session；
4. 真实窗口/剪贴板/键盘输入全局串行；
5. 输入完成立即释放全局锁；
6. 不同 session 的只读 transcript 核验可并行；
7. 每条监控循环绑定本次 start 的 epoch；stop 清队列并推进 epoch，再穿过 `delivery_lock` fence，保证 stop 返回后旧生命周期不再发生自动输入；只读核验与记账可继续。

排队从不等于许可。真正投递前必须再次核验运行状态、PID + `process_started_at`、Windows 原始 creation `FILETIME` tick、策略、额度、冷却、记录版本和 lifecycle。Windows 手动前台输入在不可逆阶段前重新核验目标代际与唯一窗口；代际不可验证时返回 `STALE_TARGET`，绝不退回裸 PID，也不能把 process handle 当成外部 console 的精确输入端点。

## 8. transcript 精确 prompt 核验

旧的 `(mtime, len)` 指纹只能证明“文件发生了变化”，无法证明本次提示词进入目标 Agent。v1.10 在投递前记录文件长度基线，只检查基线之后新增的结构化事件：

- Codex `event_msg / user_message`；
- Codex `response_item / message / role=user`；
- Claude `type=user / message.content`。

只有提取到的**整个 user message**与本次 prompt **精确相等**时，结果才是 `Landed`。数组 content 必须恰好只有一个纯文本 block；匹配文本旁存在额外文本、图片或其他 block 时拒绝。以下都不能算成功：

- 只有 mtime 变化；
- assistant/tool 簿记增长；
- 不同 prompt；
- 相同 prompt 只存在于基线之前；
- transport/API 返回成功但 transcript 没有对应 user message。

结果语义：

| Outcome | 含义 | 计数 |
|---|---|---|
| `Landed` | 本次精确 prompt 已被 transcript/协议确认 | 只此状态计入成功/催过 |
| `Silent` | transport 接受后，在核验窗口内没有本次 prompt | 失败 |
| `Failed` | transport 或定位明确失败 | 失败 |
| `Unverifiable` | 手动投递后没有可验证记录 | 不算成功，不算已确认 |
| `Deferred` | 自动模式没有安全后台通道 | 不算成功，也不算失败 |

## 9. 稳定逻辑会话与历史

Codex 只从命令行提取精确形状：

```text
codex resume <UUID>
```

然后递归寻找 `~/.codex/sessions/**/rollout-*<UUID>.jsonl`，并核验 `session_meta.payload.id` 或 `session_meta.payload.session_id`。只有 UUID、文件名和 metadata 一致时才使用稳定 ID：

```text
cx-<UUID>
```

Claude Code 同样 fail closed：只从保留参数边界的 argv 接受 `--session-id <UUID>`、`--resume <UUID>`（含等号与 `-r` 形式），并要求 cwd 对应的 `~/.claude/projects/<encoded-cwd>` 下恰好唯一命中 `<UUID>.jsonl`。裸会话、`--continue`、裸 `--resume`、冲突 UUID 或非唯一路径均不关联 transcript。

无法精确关联时使用进程代际 ID，不按 cwd 猜 transcript，更不能选择“最新文件”。历史页：

- 默认展示会话档案；逐次投递记录折叠为诊断区；
- 有稳定 session file/identity 的记录显示“逻辑会话”；
- 无法证明身份的旧记录显示“旧运行记录”；
- 一次性迁移只合并可证明属于同一旧 session ID + cwd 的碎片，不使用前端 `Set`、SQL `DISTINCT` 或 cwd 单独强行合并；
- 不删除无法安全归并的 legacy 数据。

## 10. 验收与发布边界

自动门禁至少包括：

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
pnpm test
pnpm build
git diff --check
```

真机矩阵见 `docs/manual-test.md`。Windows 自动路径应先确认外部 cmd/conhost、Windows Terminal/ConPTY 与 IDE terminal 全部安全延后；用户明确点击后，再验证前台 Unicode `SendInput` 的完整文本、独立 Enter、无剪贴板、无 PowerShell 弹窗、目标不串线以及 transcript 精确 prompt。完成之前只能表述为“代码/静态边界已对齐，Windows 手动前台路径待真机复测”。
