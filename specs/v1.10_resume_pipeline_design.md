# v1.10 两阶段续跑流水线设计

> 日期：2026-08-07
> 状态：已实现，待真实桌面验收
> 前置设计：[`v1.9_resume_coordinator_design.md`](./v1.9_resume_coordinator_design.md)

## 1. 为什么 v1.9 之后还要继续重构

v1.9 已经把扫描与续跑解耦：扫描只生成 `ResumeAction`，协调器在后台消费，因此一个会话最长
6 秒的落地核验不再冻结下一轮发现、判定和界面刷新。

但 v1.9 仍把下面整段放在同一个全局 `delivery_lock` 中：

```text
定位目标窗口 → 暂借剪贴板 → 粘贴并回车 → 恢复剪贴板 → 最长 6 秒等待记录变化
```

前四步会操作桌面级共享资源，必须严格串行；最后一步只轮询目标会话自己的 transcript，和桌面资源
没有关系。把二者绑在一起产生了新的队头阻塞：会话 A 已经完成输入、只是记录暂时没有变化时，
会话 B 的自动续跑和用户对 B 发起的手动续跑仍然要白等最多 6 秒。

v1.10 不保留这段历史临界区。核心目标是：**只串行不可逆输入，不串行只读核验。**

## 2. 资源模型

| 阶段 | 资源 | 并发规则 |
|---|---|---|
| 动作排队 | `ResumeQueue` | 同 session 合并最新快照，不堆旧动作 |
| 会话占位 | `ResumeLease` | 同 session 从出队到核验、记账、通知结束最多一个在途动作 |
| 不可逆投递 | 前台窗口、剪贴板、键盘、tmux/screen 输入 | 自动与手动共享 `delivery_lock`，全局严格串行 |
| 落地核验 | 目标 session 的 transcript 元数据 | 不同 session 并行；同 session 仍由 lease 排他 |
| 结果提交 | Rust `MonitorState` + SQLite + 通知 | 每个动作独立完成，Rust 是唯一事实来源 |

关键区别是：`delivery_lock` 保护的是**桌面共享资源**，`ResumeLease` 保护的是**会话业务闭环**。
二者不能再用同一个作用域表达。

## 3. 新流水线

```text
扫描生成 ResumeAction
        │
        ▼
ResumeQueue 按 session upsert 最新事实
        │
        ▼
pop_ready：跳过仍有 lease 的 session，继续找后面的可执行动作
        │
        ▼
取得 owned ResumeLease，并派发该 session 的任务
        │
        ├─ Phase 1：delivery_lock 内
        │    ├─ 重验 lifecycle / running / 配置 / 状态 / tactic
        │    ├─ 重验额度 / 冷却 / transcript 指纹
        │    ├─ 重验 PID + 进程启动代际 + 命令行
        │    └─ Resumer::deliver：先取 before 指纹，再定位、输入、恢复剪贴板
        │
        ├─ 立即释放 delivery_lock
        │
        ├─ Phase 2：锁外
        │    └─ Resumer::verify_delivery：只读本 session transcript，最长 6 秒
        │
        └─ 提交结果、落库、日志、通知，最后释放 ResumeLease
```

`Resumer::resume_verified` 仍作为便利入口保留，但引擎必须显式调用 `deliver` 与
`verify_delivery`，这样锁的边界在协调器里一眼可见。

## 4. 队头阻塞的消除

会话 A 核验期间仍持有 lease。新扫描可能再次为 A 生成更鲜的动作；这条动作必须保留，但不能挡住
队列后面的 B。`ResumeQueue::pop_ready` 最多检查当前队列一圈：

1. session 能取得 lease：删除并返回动作；
2. session 正忙：动作原样轮转到队尾；
3. 所有 session 都忙：返回 `None`，worker 睡眠，不自旋；
4. 在途任务结束后释放 lease 并 `notify_one`，worker 立刻重新检查保留的最新动作。

因此队列仍然有界于待处理 session 数，也不会因为一个慢核验产生 head-of-line blocking。

## 5. 安全不变式

1. **桌面输入仍全局串行。** 窗口焦点、剪贴板和键盘绝不并发使用；手动入口没有旁路。
2. **同会话闭环仍严格排他。** lease 覆盖投递、核验、记账、日志和通知，核验未结束前不会二次投递。
3. **指纹在输入前取得。** 否则快速写入可能发生在“输入完成”和“开始核验”之间，被错误判成静默。
4. **排队不授予投递许可。** 自动动作必须在拿到 `delivery_lock` 后重新验证全部可变事实。
5. **停止取消尚未输入的自动动作。** `stop()` 清队列并推进 lifecycle epoch；已派发但仍等锁的任务会在锁内重验失败。
6. **已发生的输入不可撤销。** 如果 stop 发生在真实回车之后，系统仍必须完成只读核验和记账，不能伪装成未发生。
7. **定位不确定仍不投递。** 流水线只改变调度，不放宽 `auto_follow_latest`、进程身份或窗口定位门槛。
8. **前端不重算。** `resume_pending` 与 `resume_verifying` 由 Rust 队列和 RAII 原子计数合成；前端只展示快照。

## 6. 可观测状态

`EngineStatus` 新增：

- `resume_pending`：队列中的自动动作 + 已派发、等待或执行真实投递的自动/手动动作；
- `resume_verifying`：已经完成输入、正在只读核验 transcript 的动作。

阶段计数使用 `PhaseCounter` RAII 管理，任何早退或 unwind 都会归还。`MonitorEngine::snapshot()`
把 async 状态、队列长度和原子计数合并后再返回给 Tauri；界面页脚仅在任一数字非零时展示，
不会从 sessions 反推协调器状态。

## 7. 复杂度与吞吐

- 入队 / 同 session 合并：均摊 `O(1)`；
- `pop_ready`：最坏 `O(S)`，`S` 为当前待处理 session 数；一次最多一圈；
- 内存：`O(S)`，不会随扫描次数增长；
- 桌面投递吞吐：仍受真实输入耗时约束，保证安全串行；
- 核验吞吐：从全局串行变为跨 session 并行。若 N 个会话都进入 6 秒静默窗口，核验等待由约
  `6N` 秒的串行尾延迟降为约 6 秒的并行尾延迟（不含各自真实投递耗时）。

## 8. 测试与验收

自动测试锁定：

- lease 同 session 排他、离开作用域自动释放；
- 忙 session 不阻塞后续 session，且保留最新后继动作；
- 所有 session 都忙时检查一圈后返回，不丢动作、不膨胀、不自旋；
- `PhaseCounter` 嵌套进入和所有作用域退出后归零；
- pending 为队列与投递阶段之和，verifying 独立且加法饱和；
- stop epoch、出队重验、扫描/提交归约等 v1.9 测试继续生效。

真实桌面必须按 `docs/manual-test.md` 第 13 节验证：A 在 6 秒核验时 B 能立即投递、手动 B 不等待 A、
同 session 不会重入、停止边界正确、页脚阶段数字与实际一致。未实际执行的验收项保持未勾选。
