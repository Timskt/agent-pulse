# v1.9 续跑协调器重构设计

## 背景

自动续跑是 AgentPulse 的核心价值，但旧架构把发现、检测、真实输入和最长 6 秒的落地核验全部放在
`scan_once` 的同一条等待链上。结果不仅是慢：多个会话时扫描周期会退化为 `6 秒 × 会话数`，后台
节拍、托盘和界面“立即扫描”一起排队；同时手动与自动入口各自掌握部分记账和防重语义，新增早退
分支时容易留下永久 in-flight 标记。停止守护也只是停扫描，无法成为已经排队动作的可靠取消边界。

v1.9 不保留这套历史结构。目标是把“判断现在发生了什么”和“对真实桌面执行不可逆输入”拆成两个
生命周期，并把所有安全不变式集中到 Rust 核心。

## 目标

1. 扫描耗时不再随续跑核验时间线性增长。
2. 同一会话不会因扫描频率堆积旧动作，也不会出现两个在途投递。
3. 不同会话公平排队，但剪贴板和前台窗口操作严格串行。
4. 停止守护能取消尚未执行的自动动作；停止后立即重启也不能复活旧动作。
5. 排队动作出手前必须用最新事实重新获得许可。
6. 扫描与投递并发时不覆盖续跑计数、冷却和失败退避。
7. PID 复用不能让新进程继承旧会话状态，也不能成为误投目标。
8. 手动续跑与自动续跑共享同一套幂等、投递、进程复核和结果归约语义。

## 非目标

- 不启动、托管或代理 Agent；不引入 pty wrapper。
- 不并行执行真实键盘/剪贴板投递；桌面全局资源不具备安全并行条件。
- 不放宽 `auto_follow_latest` 默认值；定位不确定仍然宁可不投递。
- 不让前端计算状态、策略或动作许可。
- 不把自动队列持久化到磁盘；重启应用后必须重新扫描、重新证明动作仍成立。

## 架构

```text
scan sources
    │
    ▼
scan_lock
    │ discover / collect / detect / merge state
    ▼
ResumeAction
(session snapshot, transcript fingerprint, stuck_secs, lifecycle_epoch)
    │
    ▼
ResumeQueue = VecDeque<session_id> + HashMap<session_id, ResumeAction>
    │ notify
    ▼
resume_worker (single consumer)
    │
    ▼
ResumeLease ── delivery_lock ── auto_action_is_current
    │                                  │
    │                                  ├─ lifecycle / running / config
    │                                  ├─ status / tactic / budget / cooldown
    │                                  └─ transcript fingerprint
    ▼
Resumer::resume_verified
    │ process PID + start time + command revalidation
    ▼
locate / deliver / verify
    ▼
commit_resume_outcome -> ResumeCommit -> storage / event / notification
```

## 核心数据结构

### `ResumeQueue`

`order: VecDeque<String>` 保存跨会话 FIFO 顺序，`actions: HashMap<String, ResumeAction>` 保存每个会话
最新动作。同一 session 再次入队只替换 map 中的快照，不重复追加 order。因此：

- 队列大小上界是待处理会话数，而不是扫描次数；
- 第一次入队决定公平顺序；
- 真正消费的永远是该 session 当前最新的检测快照；
- 即使该 session 已有一个在途动作，也只保留一条最新后继：旧动作若过期可立即接棒，若已送达则由冷却/状态重验取消后继。

### `ResumeRegistry` / `ResumeLease`

`try_acquire(session_id)` 原子占位并返回租约。租约 `Drop` 时自动释放，无论正常结束、早退、`?` 返回
还是 unwind 都不会永久卡住会话。它负责“同会话最多一个意图在执行”；跨会话真实输入仍由
`delivery_lock` 串行。

### `lifecycle_epoch`

每次有效 `start` / `stop` 都递增。`ResumeAction` 绑定生成时的 epoch，出手前必须完全相等。
`stop()` 同时清空队列。两层机制分别处理：

- 尚未出队动作：直接清队列；
- 已出队、等待投递锁的动作：epoch 不一致而失效；
- stop 后立即 start：当前 running 虽重新变为 true，旧 epoch 仍无法通过。

### 进程代际身份

裸 PID 不是稳定身份。`ProcessSnapshot.started_at` 与 PID 一起生成 session id；没有记录文件的历史键
也包含启动时刻。投递前 `process_matches_session` 只定向刷新目标 PID，并复核：

1. PID 仍存在；
2. 进程启动时刻一致；
3. 两边命令行都可读时必须一致。

这样即使命令相同的 Agent 新进程复用了旧 PID，也不会继承旧冷却/额度或接收旧动作。

## 并发状态归约

扫描开始时会复制现有 session；投递可能在扫描读盘期间完成。如果扫描随后整份覆盖状态，会把刚提交的
`resume_count`、`resume_failures`、`last_resume_at` 和 `resume_streak` 写回旧值。

`merge_resume_runtime(scanned, current, running_session_ids)` 在同一把状态锁内归约：

- 累计次数、失败次数和最后投递时间始终采用当前状态中的最新值；
- 只有本轮检测明确观察到 `Verdict::Running` 才清零自动连击；
- 其余情况保留投递任务刚更新的连击。

`commit_resume_outcome` 返回真实落笔后的 `ResumeCommit`，日志不得用动作快照自行 `+1`。

## 动作许可顺序

排队只表示“曾经值得尝试”，不表示已经获得输入许可。拿到 `delivery_lock` 后依次重验：

1. lifecycle epoch；
2. monitor running 与自动续跑总开关；
3. session 仍存在且为 `Interrupted`；
4. `ResumeTactic::Nudge`；
5. 自动连击额度；
6. 失败退避后的冷却；
7. 会话记录 `(len, mtime)` 指纹；
8. PID + 启动时刻 + 命令行。

任何一项变化都取消动作，交给下一轮扫描重新判断，绝不拿旧结论补敲。

## 手动续跑

手动动作不进入自动队列，避免用户明确点击后还排在后台动作后面；但它必须共享：

- `ResumeLease`；
- `delivery_lock`；
- `Resumer::resume_verified` 与进程代际复核；
- SQLite 记录、事件和计数归约。

手动成功增加累计续跑数并启动冷却，但不消耗自动 `resume_streak`；否则用户主动操作会挤占守护器额度。

## 验收

### 自动化

- 队列同会话合并最新动作且跨会话保持 FIFO；
- RAII 租约独占并在离开作用域时释放；
- stopped monitor 拒绝排队自动动作；
- stop/start 旧 epoch 不复活；
- 并发扫描保留已完成投递的运行态；
- 明确观察到 Running 只清自动连击，不清累计与失败状态；
- 当前进程匹配自身代际；同 PID 不同启动时刻被拒绝；
- PID 复用生成不同 session id 与历史键。

### 真机

完整未勾选清单见 `docs/manual-test.md` §13，重点包括：

- 多会话核验期间扫描和界面仍刷新；
- 手动/自动同时触发只投一次；
- 停止与 stop/start 取消旧动作；
- 会话自行恢复、退出或被替代时旧动作不投递；
- 投递期间并发扫描不丢计数、冷却与失败退避。

## 决策结果

这次重构保留了产品最重要的“非侵入”边界，却不再让该边界成为串行阻塞扫描的理由：**观察可以持续，
输入必须串行；排队可以乐观，动手必须重新证明。** Rust 仍是检测事实、动作策略和记账结果的唯一来源。
