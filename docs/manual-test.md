## 2. Windows

> v1.10 不把外部 Windows console 宣称为可按 PID 精确寻址的后台 transport。`AttachConsole` /
> `WriteConsoleInputW` 操作的是 console 级共享输入缓冲，不能保证输入只进入某个目标 CLI。因此
> classic cmd/conhost、Windows Terminal/ConPTY 和 IDE 集成终端的**自动路径都应安全延后**；
> 只有用户明确点击“续跑”后，才允许前台定位并使用 Unicode `SendInput`。以下路径尚未完成正式
> Windows 真机复测。

### 2.1 自动安全延后矩阵（P0）

| 终端 / 场景 | 自动模式预期 | 通过 |
|---|---|---|
| classic `cmd.exe` / conhost 中的外部 Codex CLI | `deferred/no-safe-transport`；不附加/写入共享 console input buffer | ☐ |
| Windows Terminal / ConPTY 中既有会话 | `deferred/no-safe-transport`；不激活窗口、不输入 | ☐ |
| VS Code / Cursor / Windsurf 集成终端 | 延后；不得把文本写进编辑器或当前终端 | ☐ |
| 多标签终端且无法精确到目标标签 | 延后；不能因标题相似而抢焦点 | ☐ |
| 无 transcript / 协议确认 | 延后；不能把 transport ACK 冒充 `Landed` | ☐ |
| PID 已退出或被复用 | 拒绝/取消；不向新进程或当前窗口补敲 | ☐ |

逐项确认：不切换前台、不抢焦点、不输入、不读取或覆盖剪贴板、不弹 PowerShell 窗口，且不增加
成功/失败统计、不消耗续跑连击。

### 2.2 用户手动点击：前台 Unicode SendInput（P0）

前置：在经典 `cmd.exe` 中启动 Codex CLI，确保进程命令行、唯一窗口目标与 transcript 能被
AgentPulse 关联。提示词建议包含 ASCII、中文、emoji 和单引号，例如：
`请继续 v1.10's check ✅`。

- [ ] 自动续跑先显示安全延后；只有点击“续跑”后才进入前台路径；
- [ ] 点击后重新核验目标进程代际；目标退出、PID 复用或窗口不唯一时明确拒绝；
- [ ] 只激活证据唯一匹配的目标窗口，不把文本写入当前编辑器、其他终端或相似标题窗口；
- [ ] 使用 Unicode `SendInput` 发送**完整提示词**，所有字符顺序正确；
- [ ] 文本事件完成后再独立发送 Enter，Codex 实际提交提示词，**不能只多一个换行**；
- [ ] 不出现 `Failed to paste image: no image on clipboard`；
- [ ] 用户剪贴板前后保持不变，不发送 `Ctrl+V` / `SendKeys`；
- [ ] 不弹出可见 PowerShell 窗口；
- [ ] transcript 基线之后出现与本次提示词精确相等的整个 user message；
- [ ] 匹配文本旁带额外文本 block 或图片 block 时不误报 `Landed`；
- [ ] 只有 mtime/assistant/tool 记录变化时不显示 `Landed`；
- [ ] 文本事件未完整发送、焦点在提交前变化或目标代际失效时明确失败，不补敲到当前窗口。

请记录：Windows 版本、终端宿主与版本、Codex CLI 版本、AgentPulse 构建、prompt、目标 PID、
窗口证据、transcript 路径、实际 outcome 和日志。

## 6. 单实例守护（v1.7，跨平台）

这一条最容易在**升级时**踩到：旧版本还在托盘里跑，新版本又装上启动，
两个进程各自守护同一批会话、各自算冷却，于是同一个终端被敲两遍提示词，
`max_resume_count` 悄悄翻倍。故障现象不是「有两个窗口」，而是
「自动续跑好像执行了两次」，很难顺着日志找到根。

| 项 | 验证点 | 通过 |
|---|---|---|
| 二次启动 | 应用已在跑时再启动一次 → **不出现第二个窗口**，原窗口切到前台 | ☐ |
| 托盘里的旧版 | 装新版前先退出旧版；忘了退也只会有一个进程在守护 | ☐ |
| 不重复续跑 | 制造一次中断 → 记录中心里那个时间点**只有一条**续跑记录 | ☐ |
| 活跃账本不被二次启动破坏 | 首实例正在投递时再次启动应用 → 第二实例退出且不得把首实例的 `delivering/transport_acked` attempt 改成 `unverifiable`；首实例仍能正常 ACK/finalize | ☐ |

## 8. 会话生命周期（v1.7）

这一节盯的是用户报过的那个 bug：**关掉的会话在历史页一直写着「运行中」**。
根因有三层，所以验的时候要分开看——只看「关掉之后标签变没变」会漏掉后两个。

| 项 | 验证点 | 通过 |
|---|---|---|
| 关掉就不再是「运行中」 | 关掉一个会话 → 下一轮扫描后档案页那行变「已结束」，并显示结束时间 | ☐ |
| 最后状态不被追改 | 那一行的「最后一眼」仍然是关掉之前的状态（比如「等你回应」），**不是**被改写成「已结束」 | ☐ |
| 状态不落后一轮 | 会话状态刚变化时，档案页显示的就是**这一轮**的状态，不是上一轮的 | ☐ |
| 重启不长新行 | 退出应用再启动 → 同一个会话**还是一行**，不是多出一行 | ☐ |
| 老库自动收拢 | 用升级前的库启动一次 → 之前被拆成多行的同一个会话合成一行，聚合数字（首次见到/续跑次数/花费）都对 | ☐ |
| 重新打开同一个项目 | 在同一个目录重开会话 → 是新的一行（新会话），不是把已结束那行改回运行中 | ☐ |

## 10. CSV 导出（v1.7）

导出这件事的失败方式很安静：文件能打开、看起来正常，但某一行的列往右串了一格，
于是「花费」那列读到的是报错信息的后半截。所以要**真的用表格软件打开看**，
不能只看有没有生成文件。

| 项 | 验证点 | 通过 |
|---|---|---|
| 四个入口 | 记录中心、档案页、花费页（每日/项目/模型）、统计页都有导出按钮 | ☐ |
| 跟着筛选走 | 先筛出几条再导出 → 文件里就是筛出来的那些，不是全库 | ☐ |
| 不跟着分页走 | 筛选结果有 50 条时导出 → 文件里是 50 行，不是当前那 20 行 | ☐ |
| 说清去哪儿了 | 导完显示「已导出 N 行」，点它能在文件管理器里亮出那个文件 | ☐ |
| 不覆盖 | 连着导两次 → 得到两个文件（文件名带时间戳），第二次没盖掉第一次 | ☐ |
| 中文不乱码 | 用 Excel 双击打开 → 中文项目名正常，不是乱码 | ☐ |
| 逗号不串列 | 找一个名字里带逗号的项目（或报错信息带逗号的记录）→ 表格里列没有错位 | ☐ |
| 多行报错 | 报错信息是多行的那条记录 → 在表格里仍然占**一行一格**，没被拆成两行 | ☐ |
| 数字可求和 | 「花费」「Token 数」两列能直接被表格软件求和，不是文本 | ☐ |
| 卡住时长 | 老记录那一列显示「未知」，不是 `-1` | ☐ |
| 空导出 | 筛到没有结果时导出 → 文件里只有表头，不是零字节 | ☐ |
| 表头跟界面同语言 | 切到 English 再导出 → 表头是英文，不是中英混排 | ☐ |
| 失败有话说 | 把下载夹改成只读再导出 → 界面说导出失败，不是静默无反应 | ☐ |
| 撞上限要出声 | 把 `EXPORT_MAX_ROWS` 临时改成 `5` 重新编译，再导一次条数超过 5 的筛选结果 → 提示变成琥珀色的「只导出了最近 5 行」，不是绿色的「已导出 5 行」 | ☐ |
| 不误报 | 承上，把筛选缩到**正好 5 条**再导 → 提示是绿色的「已导出 5 行」（一行没少，不该说还有更多） | ☐ |

## 12. 限流保持窗口（v1.8）

这一节测的是**「不做事」**，比测「做了什么」难：通过的表现是应用在一段时间里安静地什么都不
敲。所以每一项都要求你看到活动日志里那句带截止时刻的话，而不是只看到「没动静」——后者跟
守护神漏了一次长得一模一样。

必须实机测的理由：判定只读记录尾部 40 行，而保持窗口的整个存在意义就是**熬过那行限流字
被顶出 40 行之后**。单元测试能钉住时刻比较（`hold_is_active`）和形状识别
（`upstream_rejection`），但「日志一直在长、证据滚走了、它还按着」只有真实增长的记录文件
能验。窗口下限 `RATE_LIMIT_HOLD_FLOOR_SECS` 是 60 秒，所以下面几项都需要等一分钟。

**造限流现场的办法（不用真去撞限流）。** 关键是**追加的必须是合法 JSONL**：
`extract_error_text` 先 `serde_json::from_str`，解析失败的行直接 `continue`。往记录里
追加一行纯文本 `429 Too Many Requests` 是**测不到东西的**——它连检测器都到不了，
你会得出「这功能没生效」的错误结论。

Claude Code 的记录里只有三种行会被当成故障证据，任意一种都行：

```bash
S=~/.claude/projects/<项目>/<会话>.jsonl        # 换成一个已经停下来的会话

# ① system + error（最好用，content 里可以随便写话）
echo '{"type":"system","level":"error","content":"API Error: 429 Too Many Requests"}' >> "$S"

# ② apiErrorStatus（会被转成 "API Error: 429"）
echo '{"apiErrorStatus":429}' >> "$S"

# ③ isApiErrorMessage + message.content（用来试中转站的说法）
echo '{"isApiErrorMessage":true,"message":{"content":"上游负载已饱和"}}' >> "$S"
```

把证据顶出窗口用的无关行也得是合法 JSON，否则 `read_tail_lines` 照样数它 40 行、
但 `classify_turn` 会跳过——想同时保持「记录还在增长」就用真实形状的行：

```bash
for i in $(seq 50); do
  echo '{"type":"assistant","message":{"content":[{"type":"text","text":"retrying"}]}}' >> "$S"
done
```

**核心项的动作顺序不能随便改**，否则测不出东西。保持窗口的下限是 60 秒，而
`idle_timeout_secs` 默认也是 60 秒——两个窗口一样长，「按住了」和「还没到该敲的时候」
在日志上分不出来。所以第一步就要用 `retrying in 10m` 把窗口拉长，让它明显超过空闲判定：

1. 用 ① 追加 `API Error: 429 Too Many Requests, retrying in 10m` → 等一轮扫描（≤10 秒），
   日志里出现带截止时刻的那句话，**窗口现在是 10 分钟**。
2. 追加上面那 50 行，把 `429` 顶出尾部 40 行。
3. **停手，什么都别再写。** 等过 `idle_timeout_secs`（默认 60 秒）——现在文件停更、
   回合看着停下了，正常情况这就该敲字了。
4. 观察接下来几分钟：**一次投递都不该有**。这一步是整节的核心，它同时证明了两件事——
   证据已经不在窗口里了，而它依然按着。

| 项 | 验证点 | 通过 |
|---|---|---|
| 认出来会说话 | 上面第 1 步 → 活动日志出现「限流」或「上游拒绝」+ 命中的证据 + **至少到 HH:MM:SS 之前都不敲字** | ☐ |
| 证据滚走了还按着 | 上面第 2–4 步 → 停更超过空闲阈值之后**依然不投递**；滚走后开始敲字就是回归 | ☐ |
| 中转站说法也认 | 换一个会话，用 ③ 追加 `上游负载已饱和` 或 `upstream_busy`（都不在用户关键词表里）→ 同样进保持窗口，不是被当成 `RuntimeError` 去敲字 | ☐ |
| 听消息里的等待时间 | 对比第 1 步（`retrying in 10m`）和不带等待时间的一次 → 前者的截止时刻约 10 分钟后，后者是 60 秒下限 | ☐ |
| 窗口过了会自己继续 | 用不带等待时间的一次（窗口 = 60 秒下限），等窗口走完且文件已停更 → 恢复正常判定，该续跑的续跑（**不是永久静默**） | ☐ |
| 恢复干活就立刻放手 | armed 一个 10 分钟的窗口（`retrying in 10m`），然后**继续往记录里追加 assistant 行**让它看起来在干活 → 会话卡片上那行琥珀色的「撞上限流，不敲字」**马上消失**，不是等 10 分钟。状态徽标写「运行中」而下面还挂着「撞上限流」就是回归 | ☐ |
| 干完了也放手 | 承上，追加一行带完成标记的内容让它判成已完成 → 同样不再显示限流那句话 | ☐ |
| 每次认出都往后推 | 窗口快到点时再追加一行 `429` → 过了日志里写的那个时刻**仍然不敲字**（窗口被推后了）。注意日志**不会**再播一条新时刻：这条消息走 `push_event_on_change`，指纹是原因键，原因没变就不重播——所以措辞是「**至少**按到 X 之前」，X 是下限不是准确值。要看准确值就在 `apply_rate_limit_hold` 处打日志 | ☐ |
| 重启不误判 | 保持窗口生效期间重启应用 → 窗口不跨进程保留（记在内存里），但重新扫到那行 `429` 时会重新进入；不该出现「重启后立刻敲字」 | ☐ |
| 措辞不夹生 | 上述所有日志行在中文界面下是纯中文、英文界面下是纯英文，**不出现 `reason.upstream_rejected` 这种键名** | ☐ |

## 13. 两阶段续跑流水线与核心竞态（v1.10）

这一节专门验“排队仍然安全，扫描仍然灵敏，而且只读核验不再堵住下一次真实输入”。单测能证明
队列、租约、阶段计数和归约函数，但不能证明真实桌面上剪贴板、前台窗口、Agent 记录增长与多个
异步入口组合起来仍符合预期。所有测试建议先把提示词改成容易辨认且无副作用的文本，并打开活动
日志、续跑记录中心和窗口底部的流水线状态。

| 项 | 操作与预期 | 通过 |
|---|---|---|
| 自动策略不前台降级 | 在 Terminal.app、Linux 普通终端、外部 Windows cmd/conhost、Windows Terminal/ConPTY、IDE 集成终端或 screen 非精确 window 触发自动条件 → 显示“延后”，当前窗口、焦点和剪贴板不变 | ☐ |
| 手动策略才可前台 | 对同一无后台通道会话，自动先延后；随后用户点击手动续跑 → 才允许受控的前台定位/输入，未知目标仍拒绝 | ☐ |
| 连续观测 reducer | 同一结构证据未达到 `idle_threshold` 前只显示稳定性等待；证据变化或恢复健康后观察次数重置；达到阈值才生成一次 Eligible 动作 | ☐ |
| 精确 prompt 核验 | 投递后只追加 mtime、assistant/tool 事件或不同 prompt → 不得 `Landed`；基线之后追加完全相同的 user prompt → 才 `Landed` | ☐ |
| Attempt 幂等 | 同一 session generation + evidence + prompt 被多入口同时触发 → ledger 只有一个 attempt 获得真实投递许可；transport ACK 与 verified 时间分开 | ☐ |
| Deferred 记账 | 无安全 transport → attempt 为 deferred；不增加成功/失败、不消耗续跑连击、不重复刷错误通知 | ☐ |
| 稳定逻辑历史 | 同一个 `codex resume <UUID>` 跨 CLI 进程重启仍显示一条逻辑会话；同 cwd 启动两个无显式 UUID 的 Claude 会话时保持两条独立运行记录，不得共同关联“最新 transcript”；无法精确关联的数据不按 cwd 合并 | ☐ |
| 历史诊断折叠 | 历史页默认只拉取/展示会话档案；“续跑投递诊断”未展开时不挂载、不额外请求重复数据 | ☐ |
| 历史汇总跟筛选 | 切换“运行中 / 已结束”后，顶部总数、运行中数、续跑数、成本与 token 汇总跟当前状态筛选一致 | ☐ |
| 窄窗口正式验收 | 代码与静态布局已覆盖；仍需分别缩到 900×600、500×700、360×700 → 顶栏/导航/操作按钮合理换行，页面无横向滚动 | ☐ |
| 360px 极端指标 | 在 360×700 下把次数/金额模拟成超长数字 → 顶部指标卡保持两列、数字可换行且不把页面撑出横向滚动 | ☐ |
| 长文本不撑破 | 用超长路径、session ID、Agent 名、错误详情和 prompt → 卡片/Tooltip/记录行可截断或折行，按钮和中英文文案不溢出 | ☐ |
| 手动连点幂等 | 同一会话快速连点两次手动续跑 → 只投递一次；第二次明确提示“续跑处理中” | ☐ |
| 旧界面行失效 | 保留旧进程行，退出并恢复同一逻辑会话（尽量制造 PID 复用），再点旧行续跑 → 后端按不透明 `runtime_generation` 返回 stale/not found，绝不重新绑定到新进程 | ☐ |
| Windows cmd / Codex 输入通道 | 在 Windows 的 cmd.exe 中运行 Codex CLI，点“续跑” → 不弹 PowerShell 窗口；提示词以 Unicode 原样进入并提交，不能只出现一个换行；不得出现 `Failed to paste image: no image on clipboard` | ☐ |
| 手动 / 自动同刻 | 让会话恰好满足自动续跑，同时点手动续跑 → 同一会话最终只有一条真实输入和一条记录 | ☐ |

| A 核验不堵 B 投递 | 让会话 A 的记录在输入后静默、进入约 6 秒核验；此时让会话 B 自动续跑 → B 应立即进入真实投递，不等待 A 核验结束 | ☐ |

| 核验可并行、输入不并行 | A/B 都进入核验 → 两个核验窗口可重叠；但活动窗口切换、剪贴板和键盘输入仍不得重叠或串错目标 | ☐ |
| 同会话核验期间不重入 | A 核验未结束时让扫描再次命中 A，或再点一次手动续跑 → 不产生第二次真实输入；最新自动快照最多保留一条 | ☐ |
| 流水线状态诚实 | 投递排队/执行时页脚显示“待投递”，输入完成后转为“核验”；全部结束后两项消失，不能永久卡在非零 | ☐ |
| 同会话队列合并 | 让同一会话在前一动作尚未出队时被多轮扫描命中 → 只消费最新快照，不补敲旧动作 | ☐ |
| 自行恢复取消旧动作 | 动作排队后，在它出队前让 Agent 自己继续写记录 → 旧动作被取消，不再输入 | ☐ |
| 进程退出不误投 | 动作排队后退出 Agent → 出队时拒绝投递，不把提示词敲进剩下的前台窗口 | ☐ |
| PID 复用不继承 | 旧 Agent 退出后启动新进程（若系统复用 PID）→ 新会话 id/历史键不同，不继承旧冷却、失败退避或自动连击 | ☐ |
| 停止清队列 | 多会话排队时点“停止守护” → 尚未投递的自动动作全部不再执行 | ☐ |
| 停止发生在核验阶段 | 某动作已经真实回车并进入核验后点“停止守护” → 不再派发尚未输入的动作；已输入动作仍完成核验与记账，不能伪装成没发生 | ☐ |
| stop fence | 在自动投递刚越过许可检查时点击停止 → 停止调用等待不可逆输入结束；停止返回后不再出现旧输入 | ☐ |
| stop/start 不复活 | 在通道体检等待期间停止后立刻重新开始守护 → 旧 start 不会复活成第二条扫描循环；旧动作仍不能执行 | ☐ |
| 停止不禁手动 | 守护停止时点手动续跑 → 仍可按用户明确意图执行（但仍受会话租约、定位和进程复核约束） | ☐ |
| 后续动作出队重验 | 多会话排队时修改开关/额度/冷却，或让后续会话恢复 → 后续动作按出队时事实取消，不按旧快照补敲 | ☐ |
| 并发扫描不丢账 | 续跑正在落地核验时触发扫描 → 完成后 `resume_count`、`last_resume_at`、失败退避与冷却不回退 | ☐ |
| 跨会话串行 | 两个会话同时中断 → 剪贴板和前台窗口操作不重叠，每条输入都落到各自目标 | ☐ |
